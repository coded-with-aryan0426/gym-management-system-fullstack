## Why Migrate from Oracle?

| Factor | Oracle XE | PostgreSQL |
|--------|-----------|------------|
| **License cost** | Free for XE (11GB limit), enterprise = $$$$ | ✅ 100% free, unlimited |
| **Cloud hosting** | Oracle Cloud only (limited options) | ✅ Every cloud provider |
| **Community** | Small, enterprise-focused | ✅ Massive open-source community |
| **Cloud-managed options** | Oracle Autonomous DB only | ✅ Railway, Render, Supabase, Neon, AWS RDS, all free tiers |
| **Docker support** | Heavy Oracle images (~8GB) | ✅ Alpine image (~60MB) |
| **ORM compatibility** | Oracle dialect (specific) | ✅ PostgreSQL dialect (universal) |
| **Scaling tools** | Expensive add-ons | ✅ PgBouncer, read replicas, Citus for free |
| **Data limit** | XE = 11GB max | ✅ Unlimited |
| **Full-text search** | Oracle Text (complex setup) | ✅ Built-in tsvector |
| **JSON support** | Oracle JSON (different syntax) | ✅ JSONB (superior) |

## Migration Plan: Oracle → PostgreSQL

### Phase 1: Schema Conversion

#### Automatic Type Mapping

| Oracle Type | PostgreSQL Equivalent |
|-------------|----------------------|
| `NUMBER` | `BIGINT` or `NUMERIC` |
| `NUMBER(1)` (boolean) | `BOOLEAN` |
| `NUMBER(5,2)` | `NUMERIC(5,2)` |
| `VARCHAR2(n)` | `VARCHAR(n)` |
| `CLOB` | `TEXT` |
| `BLOB` | `BYTEA` |
| `TIMESTAMP` | `TIMESTAMP` |
| `DATE` | `DATE` |
| `NUMBER GENERATED BY DEFAULT AS IDENTITY` | `BIGSERIAL` or `GENERATED ALWAYS AS IDENTITY` |

#### Key Syntax Differences
```sql
-- Oracle
CREATE TABLE users (
    user_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR2(100),
    is_active NUMBER(1) DEFAULT 1,
    CONSTRAINT chk_active CHECK (is_active IN (0, 1))
);

-- PostgreSQL equivalent
CREATE TABLE users (
    user_id BIGSERIAL PRIMARY KEY,
    full_name VARCHAR(100),
    is_active BOOLEAN DEFAULT TRUE
);
```

### Data Volume Estimation

| Metric | Per Gym/Month | 500 Gyms/Month | 500 Gyms/Year |
|--------|---------------|-----------------|----------------|
| Members | 200 avg | 100,000 | 100,000 |
| Transactions | 500 | 250,000 | 3,000,000 |
| Messages | 2,000 | 1,000,000 | 12,000,000 |
| Sessions (PT) | 400 | 200,000 | 2,400,000 |
| Progress metrics | 1,000 | 500,000 | 6,000,000 |
| Check-ins | 6,000 | 3,000,000 | 36,000,000 |
| Notifications | 5,000 | 2,500,000 | 30,000,000 |
| **Total rows/year** | | | **~90M rows** |
| **Estimated storage** | | | **~50GB** |

### Scaling Techniques

#### 1. Connection Pooling (PgBouncer)
```
App → PgBouncer (pool: 20 connections) → PostgreSQL (max: 100)
```
Handles 500+ concurrent requests with limited connections.

#### 2. Read Replicas
```
Primary (write) → Replica 1 (read) → Replica 2 (read)
```
Route read queries (dashboards, reports) to replicas.

#### 3. Table Partitioning
```sql
-- Partition large tables by gym_id
CREATE TABLE messages (
    message_id BIGSERIAL,
    gym_id BIGINT NOT NULL,
    ...
) PARTITION BY HASH (gym_id);

CREATE TABLE messages_p0 PARTITION OF messages FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE messages_p1 PARTITION OF messages FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... up to p7 (8 partitions)
```

#### 4. Archival Strategy
```sql
-- Move old data to archive tables
CREATE TABLE messages_archive (LIKE messages INCLUDING ALL);

-- Monthly archival job
INSERT INTO messages_archive 
SELECT * FROM messages WHERE created_at < NOW() - INTERVAL '6 months';

DELETE FROM messages WHERE created_at < NOW() - INTERVAL '6 months';
```

#### 5. Caching Layer (Redis)
```
Redis Cache Strategy:
├── Dashboard stats: TTL 60 seconds
├── User session: TTL 30 minutes
├── Gym settings: TTL 5 minutes
├── Class schedules: TTL 1 minute
├── Notification counts: TTL 30 seconds
└── Search results: TTL 2 minutes
```

#### 6. Indexing Strategy
```sql
-- Critical indexes for 500-gym scale
CREATE INDEX idx_messages_gym_created ON messages(gym_id, created_at DESC);
CREATE INDEX idx_checkins_gym_date ON check_ins(gym_id, check_in_time DESC);
CREATE INDEX idx_transactions_gym_date ON transactions(gym_id, created_at DESC);
CREATE INDEX idx_pt_sessions_gym_trainer ON pt_sessions(gym_id, trainer_id, session_date);
CREATE INDEX idx_memberships_gym_status ON memberships(gym_id, status, end_date);
CREATE INDEX idx_notifications_gym_user ON notifications(gym_id, user_id, is_read, created_at DESC);

-- Partial indexes for common queries
CREATE INDEX idx_active_memberships ON memberships(gym_id, user_id) 
    WHERE status = 'ACTIVE';
CREATE INDEX idx_unread_notifications ON notifications(gym_id, user_id) 
    WHERE is_read = FALSE;
```
